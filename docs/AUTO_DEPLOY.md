# Automatic production deployment

The `Valcairn CI and deploy` workflow checks pull requests into `master`, every push to `master`, and manual dispatches. It deploys only the checked revision of this repository's `master`, after all three CI jobs succeed:

- `Web / no database`: install the lockfile, run the build plus tests without database variables, run the standard-library Python release-controller unit tests, and build the production web and migration Docker images.
- `Web / PostgreSQL 17`: run the same checks against a disposable, loopback-only `valcairn_ci_test` database.
- `Ingest / Rust 1.99.1`: install the pinned toolchain including clippy, lint with warnings denied, run locked tests and build the production ingest image.

These Docker builds test the actual packaging boundary, not only code checked out by CI. The web build stage must include `src/lib/onboarding.js`, which is imported by `web/src/app/project.jsx`; omitting it can pass a repository build while failing the production Docker build. Images use CI-only tags and are not pushed by these checks.

Pull-request jobs never receive the production environment or deployment key. There is no `pull_request_target` workflow, untrusted checkout in a privileged job, personal SSH key, or production database connection in CI. Official actions are pinned to full commit SHAs.

## One-time configuration

Configure the GitHub **production environment** with a deployment branch policy allowing only `master`. Automatic deployment needs no required human approver; retain repository PR review and require the three CI checks through the existing branch-protection/ruleset process.

Set these environment variables through repository settings or `gh variable set --env production`:

| Variable | Value |
| --- | --- |
| `DEPLOY_HOST` | The approved VPS hostname or IPv4 address |
| `DEPLOY_USER` | The dedicated, locked-down deployment SSH account |
| `DEPLOY_KNOWN_HOSTS` | The previously verified OpenSSH host-key entry for exactly that hostname/address |

Set the environment secret `VALCAIRN_DEPLOY_KEY` to a **new deployment-only private key** through a protected file or stdin. Do not copy the user's personal VPS private key into GitHub. Never print either key. Do not run `ssh-keyscan` during CI and trust its answer automatically; update the pinned host key only after independently verifying a server identity change.

The deployment account's authorized key must force the server's fixed deployment-request command, disable PTY/agent/port/X11 forwarding and user rc, and have no general shell or Docker access. The server-owned command accepts only `deploy <40-lowercase-hex-SHA>`. It must validate the request again, take a deployment lock and independently confirm that the SHA is the current `master` head of the fixed repository. A stale or invalid request must not deploy arbitrary code. The helper checks the three completed CI jobs for that exact SHA; it does not wait for the overall workflow to finish because deployment itself belongs to that workflow. It checks master again after building and before migrating.

The deploy job has no checkout and sends no script, archive, environment values or production credentials to the VPS. Its only remote request is the SHA. Runtime environment variables remain in the existing VPS secret files and container configuration; this workflow introduces no application environment variables.

## Server deployment contract

The forced command invokes the root-owned release helper installed by the operator. Follow `docs/RELEASE.md`; CI success does not waive its production safeguards.

1. Validate the fixed repository, exact current master SHA and successful required CI jobs; serialize deploys with a server lock. Before the backup, the helper measures free space on the release root, the Docker data root and the database container's mounts and stops unless each has at least the larger of `min_free_bytes` (deployment-config key, default 5 GiB) and three times the live database size. This is a floor, not a capacity plan: the operator still confirms room for the dump, scratch restore and three image builds.
2. Snapshot the current web/ingest image references and protected runtime configuration for rollback. Never log secret values.
3. Back up the production database and restore it into a uniquely named scratch database. Verify the restored data before changing production. A dump file alone is not sufficient. Scratch deletion must be explicitly confined to the newly created scratch database, never the live database. Presence, the migration ledger and the per-table fingerprints are read in the one exported snapshot that `pg_dump --snapshot` reuses, so the fingerprint and the dump describe the same instant. Which tables must exist is decided by the migration ledger, group by group (the ledger table plus 13 tables at the supported `006` baseline, 27 tables through `013`): a listed migration whose tables are missing, or tables without their ledger entry, stops the release, and every present known table is fingerprinted. The receipt lists the tables actually verified and the groups not yet present; absent tables are never reported as restore-tested.
4. Build migrator, ingest and web images from the same requested revision, with immutable SHA tags and revision labels.
5. Apply pending numbered migrations with the separate migrator role. Check the migration ledger and require a second run to apply zero. Changed applied checksums are fatal. Both migration passes and every SQL helper container run on the approved network with the migrator secret file, the CA mount and the live web container's custom host mappings (`HostConfig.ExtraHosts`, repeated as `--add-host` arguments after validation, never logged), so the configured database hostname and its TLS identity stay exactly as the web uses them; the offline catalog validation keeps `--network none` and carries none of these. Before and after the migration the helper digests the records a migration may not touch (reviewer accounts, reviews, versions, frozen projects, and when present requested enhance plans, capital submissions, credit records and review marks); any changed or vanished record stops the release. Digests stay inside the helper and never reach the receipt or logs; only row counts are recorded.
6. Confirm application grants, then execute the read-only operator box query from the release. The query is in `scripts/sql/`; the current migrator image does not include that directory, so mount the checked release query read-only or use the release checkout. Never silently substitute a different query. Validate the constraint only when no violations remain; preserve invalid frozen history and leave `NOT VALID` when required.
7. Preserve the already-provisioned YC, Speedrun and admin reviewer records. Do not reset or re-provision credentials during every deployment.
8. Roll the single ingest instance, preserving private storage, network, credentials and routing; verify it. Roll web last, preserving all environment values, mounts, TLS, sessions, staff list, sign-in log and routing.
9. Confirm the deployed revision and public health/pages/CSP. A replaced container counts as ready only when Docker's own health status is `healthy` (when the image defines a HEALTHCHECK; `starting` waits, `unhealthy` fails) and its internal `/healthz` answers, within a bounded time; public checks never follow a redirect, require every answer (including the preview refusal) to come from the exact requested origin (scheme, host, port) and endpoint, retry only transient transport failures and 502/503/504 within a bounded budget that caps each request and is checked before every attempt, keep TLS verification, and treat every other failure (redirect, wrong origin, certificate or protocol error, CSP drift, a preview route that accepts an invalid token, a termination request) as final at once. Revert web/ingest to their recorded prior tags if the rollout fails; the receipt records the original failure, whether the previous containers were restored, and any verification failure during rollback separately. Never remove approved data or edit an applied migration as a rollback shortcut.

### Feature tables, grants and catalogs

Tables are grouped by the numbered migration that creates them: `001` (`users`, `email_codes`, `workspaces`, `memberships`, `invitations`, `join_requests`, `projects`, `audit_events`), `002` (`sessions`), `004` (`uploads`, `reviews`, `dataset_versions`), `006` (`reviewer_accounts`), `007` (`annotations`, `issue_notes`), `011` (`model_pulls`, `enhance_runs`), `012` (`devices`, `device_reports`, `model_installs`, `execution_runs`) and `013` (`capital_cases`, `capital_submissions`, `credit_records`, `capital_evidence`, `capital_review_marks`); `003`, `005` and `008` to `010` add none, and `schema_migrations` belongs to the migrator. The ledger decides what must exist: a listed migration requires its whole group and an unlisted one forbids it, so the documented `001`-`006` production (reviewer accounts provisioned, dataset workspace not yet applied) backs up, restores and then receives every pending migration through `013` in order, while a database already at `011`-`013` is fingerprinted, frozen-record checked and granted, all without a source change. `006` is the supported baseline because the preflight reads reviewer accounts. The `011`-`013` groups match the migrations on `master` (`013_capital.sql` landed with the Capital store); a ledger that disagrees with the tables stops the release rather than passing. A unit test keeps every group equal to the `CREATE TABLE` statements of the migration files present in `migrations/` (`001`-`013` on `master`), and the optional real-database proof applies `001`-`013` and exercises the grants and frozen-record queries on that schema.

The application role itself must be a plain least-privilege login, and the preflight checks this before the backup, build, grants and migrations, whatever tables exist yet: not a superuser and without `CREATEDB`, `CREATEROLE`, `BYPASSRLS` or `REPLICATION`; not the owner, directly or through an inheriting or `SET`-capable membership, of any table, sequence or view in `public` or of the database; not a member of the migrator role or of any `pg_*` predefined role; unable to `SET ROLE`, directly or through any chain of memberships, to a role that has any of those cluster privileges (attributes are never inherited, but `SET ROLE` makes them usable, so a custom `NOLOGIN` group with `CREATEDB` granted `WITH SET TRUE` is refused); and holding no `ADMIN` option on any role, neither directly nor through any identity it can assume (`SET`) or inherit (`USAGE`): an `ADMIN` option lets that identity grant memberships, so a powerless hop that administers a privileged group would let the app wire its own path to the powers, and administering even a powerless group is a membership mutation outside the contract. A membership that confers none of these, for example an inheriting but `SET`-disabled one in a group that owns nothing and administers nothing, stays allowed and is only recorded in the receipt. The same owner test is applied per table during the grant check, so an owner that trimmed its own ACL to exactly the contract is still refused (it can alter, drop and re-grant at will). The helper reports and stops; it never revokes, reassigns or alters roles.

Grants are explicit per table and derived from the statements the application store issues: `SELECT, INSERT, UPDATE, DELETE` on `annotations` and `issue_notes` as before; `SELECT, INSERT` on `model_pulls`, `device_reports`, `execution_runs`, `credit_records` and `capital_review_marks`; `SELECT, INSERT, UPDATE` on `enhance_runs`, `devices`, `model_installs`, `capital_cases` and `capital_submissions` (row locks need `UPDATE`); `SELECT, INSERT, DELETE` on `capital_evidence`. Before and after the migration the helper asks PostgreSQL for the app role's *effective* privilege on every table privilege (`SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER`, plus `MAINTAIN` on PostgreSQL 17 and later), which includes grants, role membership and ownership. Anything held beyond the contract, including `TRUNCATE` on an append-only table (which no row trigger stops), table ownership by the app role or a superuser app role, stops the release before any grant or migration; the operator revokes or re-owns, the helper never revokes. It then grants only the missing contract statements on tables that exist, never schema-wide or `ALL` privileges and never `DELETE` on append-only or frozen records, and stops if a contract table owns a sequence (none do; all use uuid defaults). The app and migrator roles stay separate. The mocked unit tests cover these rules; the real SQL (ledger and presence in one snapshot, `has_table_privilege` over the full set, owner and superuser detection, sequence discovery, row locks needing `UPDATE`) is exercised by the optional `PostgresSemantics` test when `RELEASE_GUARDS_TEST_DATABASE_URL` names a local, dedicated `*_test` database; it is skipped otherwise, so CI's no-database job proves only the mocked rules.

Catalog files are deployment data, not part of the image. If the live web container sets `MODEL_CATALOG_FILE` (workspace Models catalog) or `LOCAL_MODEL_CATALOG_FILE` (download options for the visitor's own runtime), each path must come from a read-only container mount, be a readable JSON file, and the two must be distinct files. After the images build, the helper parses the mounted files with the candidate release's own `loadConfig` in a throwaway container with no network, only those read-only mounts and a random throwaway session secret; a rejected catalog stops the release before the web swap. The receipt records the container path, host path, SHA-256 and size per catalog, never the contents. The files are re-digested just before the web swap, and the helper never creates, edits or unsets a catalog: the previous container keeps its own mounts for rollback, and an unset catalog stays unset. `LOCAL_RUNTIME_ORIGINS` and `LOCAL_MEMORY_ORIGINS`, when set, must contain only loopback `http://` origins, and no Provena or memory key, token or secret variable may be present in the web environment: local-memory credentials live on the visitor's device only. The helper preserves whichever value the live container has and never adds, defaults or clears one; note that the current build treats an unset `LOCAL_MEMORY_ORIGINS` as its default loopback gateway origins (Memory and Agents pages on) and only an explicitly empty value as off, so the operator decides that before the rollout (`docs/RELEASE.md`).

The branch protection and required-check rulesets on `master`, the production environment values, and authenticated live QA with synthetic accounts remain operational setup outside this repository. Passing checks on the pull request that carries this workflow do not make it active on `master`; this document and the helper tests change no CI, ruleset or production configuration.

The production helper and its installation are deliberately outside the workflow's credential boundary. The workflow must remain disabled/unconfigured until that helper, scoped key and backup/restore procedure have been verified. A successful SSH connection is not proof that a release passed its health checks.

## Concurrency, failure and recovery

GitHub permits one running and one pending job in the `valcairn-production` group. A later pending request can supersede an older pending request; running deployment is **not** canceled automatically. The server lock provides a second boundary for manual requests. If master advances before a queued revision begins, the current-master check should reject the stale request; the newer successful workflow remains responsible for deploying the new head.

An interrupted SSH connection is not permission to start a second deployment or assume rollback completed. Check the server receipt and lock state first. Prefer a server-managed job/receipt if the installed helper continues asynchronously; CI must wait for and check its terminal result before reporting success.

Inspect Actions for the checked commit's three CI jobs and deployment result. The release receipt should identify the requested/deployed SHA, prior/new image tags, backup/restore proof, migration files, operator result and health checks without including secrets. Authentication-dependent live QA still requires approved QA access; do not reset reviewer accounts or create customer data to make an unattended deploy appear fully verified.

To recover manually, retain the previous image tags and follow `docs/RELEASE.md`. Database restoration is a separately verified operation into a fresh database, not an automatic destructive rollback. Never use `npm audit fix --force` in deployment.

## Verification of this workflow

Before enabling it: review the YAML, validate its shell, verify the action SHAs against their official repositories, and test the forced command's rejection of malformed/stale requests. Then run the real PR CI and a master deployment, inspect the server's sanitized receipt and verify the deployed revision. A locally parsed YAML file alone is not end-to-end proof.
